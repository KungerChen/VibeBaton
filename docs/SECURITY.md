# VibeBaton Security Model & Trust Boundaries

> **TL;DR**: VibeBaton's **Path Whitelist Guard** is a post-hoc Git worktree audit & revert mechanism — **NOT an OS-level kernel sandbox**. Running unattended overnight pipelines on your host machine is intended **only for repositories you trust**.

---

## 1. Threat Model & Trust Boundaries

### What Path Whitelist Guard Protects Against
- Accidental or out-of-scope file edits inside the target repository by worker agents (`routine` / `critical` tasks).
- Leftover dirty files or stray tool caches leaking across sibling parallel worktrees or onto `main`.

### What Path Whitelist Guard Does NOT Prevent on the Host
To avoid interactive `[y/N]` stalls during unattended overnight runs, local CLI providers may be invoked with non-interactive flags configured in `baton.toml` / `baton.example.toml` (for example, `claude --dangerously-skip-permissions`, `codex exec -s workspace-write -c approval_policy="never"`, or `dsh --permission-mode workspace-write --approval-policy never`).

Because `claude` and shell commands execute under your local OS user account:
- **Untrusted repositories / Prompt Injection**: Malicious instructions embedded in third-party READMEs, issues, code comments, or dependency scripts could instruct an agent to read sensitive local files (such as `~/.ssh`, cloud credentials, or `.env` files outside the worktree), delete files outside the repo, or make outbound network requests.
- **Post-hoc vs. Pre-execution**: Git whitelist checking runs *after* a CLI turn exits, so side effects outside the git worktree or over the network cannot be rolled back by Git.

### Safe Usage Rules
1. **Host execution**: Only run unattended pipelines directly on the host against **your own trusted repositories** and inspected dependencies.
2. **Untrusted repositories**: Always run VibeBaton inside an isolated VM, Windows Sandbox, or the turnkey **Docker / DevContainer sandbox** generated by `baton sandbox init --repo .` (see [Container Sandbox](#container-sandbox-stage-4-v100)).
3. **Human-in-the-Loop Anchors**: Keep `require_human_approval_at = ["rfc_signoff", "plan_amendment", "final_merge"]` enabled so AI milestones never auto-merge directly into `main` without L0 / human review.

## 2. Provider Terms & Polite Rate-Limit Scheduling

VibeBaton is explicitly designed to **respect provider rate limits and terms of service**, never to bypass them:
- **Conservative Concurrency**: Subscription CLI providers default to `max_concurrency = 1` in `baton.example.toml`.
- **Active Cooldown Backoff**: On detecting `429` / usage-limit / quota responses, VibeBaton pauses only the throttled provider using exponential backoff (`cooldown_backoff_sec`) in SQLite and resumes cleanly once the quota window resets.
- **First-Class API Support**: Pay-as-you-go APIs (e.g. OpenCode Go, DeepSeek API, and Stage 4 native OpenAI-compatible HTTP providers) are treated as first-class citizens alongside local CLIs.

---

## 3. Local Web UI & Secret Hygiene

- **Localhost Only by Default**: `baton ui` binds strictly to `127.0.0.1` (do not expose it directly to untrusted public networks without authentication/reverse proxy).
- **Path Traversal Guards**: Static asset serving, RFC path resolution (`/api/runs/start`), and graph validation reject path traversal outside the repository or static build directory.
- **Zero-Secret Repo Policy**: Never store API keys or tokens in `.baton.json`, `baton.toml`, or `.patch.yml` overlays committed to Git. Credentials stay in OS environment variables or local credential stores (such as `~/.dsh/.credentials.yaml`), and runtime `.baton/state.sqlite*`, `.baton/logs/`, `.baton/runs/` are `.gitignore`d.

## Container Sandbox (Stage 4, v1.0.0)

`baton sandbox init --repo . [--force]` writes the sandbox files and exports a runtime archive from the VibeBaton instance that runs the command. Both launch paths build the image with that archive installed at `/opt/vibebaton`. The target repository is mounted at `/workspace` at runtime.

### Generated files

| File | Purpose |
| --- | --- |
| `sandbox/Dockerfile` | Python 3.12 / Node LTS image with Git and VibeBaton installed. The image runs as the unprivileged `baton` account. |
| `sandbox/docker-compose.yml` | Compose service that applies every runtime hardening control listed below. |
| `.devcontainer/devcontainer.json` | Dev Container definition that builds the same image, connects as `baton`, and checks the installed CLI with `python -P -m vibebaton --help`. |
| `sandbox/vibebaton-runtime.zip` | VibeBaton's Python package and bundled CLI resources, including the example configuration, prompts, and presets from a source checkout. |
| `sandbox/.dockerignore` | Limits the `sandbox/` build context to the runtime archive and Docker's build metadata. |
| `.vibebaton-empty/.gitkeep` | Creates the directory used for the default read-only credentials mount. |

### Build and run

Run these commands from the target repository with a trusted VibeBaton CLI and Docker BuildKit.

```sh
baton sandbox init --repo .
docker compose -f sandbox/docker-compose.yml run --build --rm vibebaton
```

The container prints `baton --help`. In a Dev Container, use the generated configuration after running the same scaffold command. Run the scaffold command before the first build of the checked-in VibeBaton templates to generate the runtime archive. The archive is the only application input to the Docker build. BuildKit mounts it read-only during installation. [Docker build context](https://docs.docker.com/build/concepts/context/), [BuildKit bind mounts](https://docs.docker.com/reference/dockerfile/#run---mounttypebind).

The command preserves existing files by default. Review preserved scaffold files and the archive before building from an untrusted repository. Use `--force` when you intend to replace the scaffold, including when upgrading templates or refreshing the bundled VibeBaton version.

### Hardening controls

**Docker Compose** (`sandbox/docker-compose.yml`) applies every control listed below. **Dev Container** (`.devcontainer/devcontainer.json`) builds the same image, runs as `baton`, drops every capability, and sets `no-new-privileges`. Compose alone configures the read-only root filesystem and `tmpfs` mounts.

- **Non-root `baton` user (UID 1000)**. The image sets `USER baton` with UID/GID 1000. Compose pins that identity, and Dev Container keeps it with `updateRemoteUserUID: false`. On Linux, the bind-mounted repository must grant UID or GID 1000 write access for editing.
- **Capabilities**: `cap_drop: [ALL]` drops every Linux capability.
- **No privilege escalation**: `security_opt: [no-new-privileges:true]` prevents setuid / setgid binaries from gaining additional privileges.
- **Read-only root filesystem with tmpfs** (Compose only). `read_only: true` makes the image filesystem read-only. The writable scratch mounts are `/tmp` and `/home/baton/.cache`. Tools that write elsewhere under `$HOME` need to direct those writes to a writable location.
- **Repository mounted at `/workspace` only**: Compose mounts the repository root with `..:/workspace:rw`. This is a read-write bind mount, so changes made to files under `/workspace` inside the container are written back to the host repository. Apart from the optional read-only credentials directory below, no host home directory, Docker socket, or other host path is mounted.
- **Credentials**: injected through environment variables (for example `OPENAI_API_KEY` and `DEEPSEEK_API_KEY`) or a read-only `~/.vibebaton` mount (`VIBEBATON_CREDENTIALS_DIR`, mounted with `:ro`).
- **Zero `~/.ssh` mount**: SSH keys are never mounted into the container.

### What this does NOT protect against

- Container runtime or kernel escapes, or a compromised Docker daemon (never mount the Docker socket into the sandbox).
- Network egress or data exfiltration performed by code running inside the container.
- Credentials deliberately exposed to the sandbox through environment variables or the read-only `~/.vibebaton` mount; the sandboxed process can still read them.
- Vulnerabilities in the base image or in third-party packages installed at build time.
- Side effects outside Git: the path whitelist audit still runs post-hoc and cannot roll back changes made outside the worktree.
